# biome-plugin-suitescript

[![npm version](https://img.shields.io/npm/v/biome-plugin-suitescript)](https://www.npmjs.com/package/biome-plugin-suitescript)
[![CI](https://img.shields.io/github/actions/workflow/status/nemchik/biome-plugin-suitescript/ci.yml?branch=main&label=CI)](https://github.com/nemchik/biome-plugin-suitescript/actions/workflows/ci.yml)
[![license](https://img.shields.io/npm/l/biome-plugin-suitescript)](LICENSE)

[Biome](https://biomejs.dev) lint plugins and a tag checker for NetSuite **SuiteScript 2.1**, ported from
[acdvs/eslint-plugin-suitescript](https://github.com/acdvs/eslint-plugin-suitescript) and
[btonasse/eslint-plugin-suitescript](https://github.com/btonasse/eslint-plugin-suitescript).

Requires Biome **>= 2.6.4** (npm-distributed plugins use `biome-manifest.json`) and Node >= 24 for the CLI. Node 24 LTS is also what Oracle's
[SuiteCloud CLI for Node.js requires](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1558708810.html).
Rules work on both AMD `define()` and ES `import`/`export` source, in `.js` and `.ts`.

## Install

```sh
npm i -D @biomejs/biome biome-plugin-suitescript
```

## Use

Extend one of the three configs. Each turns on the matching plugin preset, Biome's own recommended rules and the
native Biome rules that Oracle's documentation or agent skills ask for, and declares the SuiteScript globals
(`define`, `require`, `log`, `util`):

```jsonc
// biome.json
{
    "extends": ["biome-plugin-suitescript/configs/recommended"],
    "plugins": [
        "biome-plugin-suitescript/noLogModule" // add individual rules on top
    ]
}
```

| Config                                         | Enables                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| `biome-plugin-suitescript/configs/minimal`     | `presets/minimal`, Biome's recommended rules (with `noUnusedFunctionParameters` off) |
| `biome-plugin-suitescript/configs/recommended` | `presets/recommended`, plus the native rules marked :green_circle: below             |
| `biome-plugin-suitescript/configs/all`         | `presets/all`, plus every native rule marked below                                   |

The plugin presets (`biome-plugin-suitescript/presets/<name>`) alone only list this package's rules, because a
Biome plugin preset cannot enable native rules. Use them in `plugins` if you want to choose the native rules
yourself. `configs/suitescript2` only declares the globals.

Biome's `noUnusedFunctionParameters` is off in all three configs: a `define()` callback takes one parameter per
dependency (`noExtraParams`), so a module loaded for its side effects would otherwise be reported.

Run the tag checker beside `biome check` (see [Tag checker](#tag-checker)):

```sh
npx biome-plugin-suitescript check
```

## Rules

Each rule has one fixed severity: `error` for things that fail at runtime or on upload, `warn` for conventions.
Biome plugins cannot be reconfigured per project, so you choose by enabling rules, scoping them, or generating one.
Rules are sorted by source tier, then severity, then preset, then name. How a rule's tier and place in a preset are
decided is in [docs/rule-priority.md](docs/rule-priority.md).

### Opt-in rules and typings

The rules marked :key: are in no preset, because each one guesses and may misfire. Add the ones you want to
`plugins` yourself, for example `"biome-plugin-suitescript/noHardcodedSecrets"`. The reason each is left out is in
the table. `noHardcodedSecrets` matches names (`password`, `passwd`, `pwd`, `secret`, `apiKey`, `clientSecret`,
`tokenSecret`, `consumerSecret`, exact match only) rather than knowing a value is a credential. Oracle says "Don't
hard-code any passwords in scripts." Biome's `noSecrets`, which matches known token formats and high-entropy strings
instead, is not enabled in any config: on a real-world SuiteScript codebase (286 files) it reported 282 times, nearly
all false positives (log messages, NetSuite URLs, minified vendor files). Enable it yourself if you want it.

The rules assume you type-check against [`@hitc/netsuite-types`](https://github.com/headintheclouddev/typings-suitescript-2.0)
(the repository is named `typings-suitescript-2.0` but the typings are written for SuiteScript 2.1; the repository was
never renamed). They are credited as Tier 2 where a rule follows them, and they already reject wrong option names, missing parameters and positional-argument calls to N/ methods (their
signatures take an options object). For plain JavaScript projects, which get nothing from the typings, five rules
generated from the typings cover module-level functions and enums: `requireOptions`, `noUnknownOptions`,
`noPositionalOptions`, `noInvalidEnumMember` and `noUnknownModuleMember`. They resolve `record` in `record.load(...)`
from the `define()` or `import` binding, so they only fire on an `N/` module you loaded. Instance methods
(`rec.setValue`, `form.addField`) need the receiver's type, so only the hand-written `require*Options` rules look at
those, by name. The typings can lag a NetSuite release, so `noUnknownModuleMember` can report a member Oracle added
recently; refresh the data with `npm run sync-typings` after updating `@hitc/netsuite-types`.

### Logging and `N/log`

Oracle's help center says "NetSuite loads the log Object by default for all script types. You do not need to load it
manually", so `noMissingModules` leaves `log` (and `util`) alone. Oracle's two skills disagree: the upgrade skill says
the global exists but loading it is recommended, the learning skill says it is not global (the higher-ranked upgrade
skill and the documentation win). Two opposite styles are therefore available, and you should enable only one:
`requireLogModule` (in `all`) wants `N/log` loaded whenever `log.*` is used, following the upgrade skill's
recommendation; `noLogModule` (opt-in) wants the global.

### Native Biome rules

Rules Biome already ships are not reimplemented. `configs/recommended` enables `noGlobalEval` and `noImpliedEval` for
Oracle's OWASP skill, and `configs/all` adds the "Modernize JavaScript" rules from the upgrade skill
(`noVar`, `useConst`, `useTemplate`, `useIncludes`, `useForOf`). `noImpliedEval` and `useIncludes` are Biome nursery
rules, which may change or be renamed in a Biome release. `noBrowserGlobals` flags `alert` only in server scripts,
which Biome's `noAlert` cannot do because it has no notion of a script type.

### `entryPoints` and script types

Biome plugins cannot read comments, so the script type is **inferred from what the module returns**
(`beforeLoad` → User Event, `onRequest` → Suitelet, ...). The rule reports mixed entry points
(`pageInit` with `execute`) and missing required ones (Map/Reduce needs `getInputData` and `map` or `reduce`).
Modules that return no distinctive entry point are libraries and are ignored. Generic names such as
`get`, `post`, `map` and `run` alone never make a module a script. `noWrongScriptTypeModules` follows Oracle's
"Supported Script Types" table, except for `N/ui/message`: the table lists it as client-only, but Suitelets and user
event `beforeLoad` scripts load it to build the message `Form.addPageInitMessage` shows, as Oracle's own FAQ sample
does.

### Choosing what to enforce

- **Pick rules.** `log-args`' two options are the separate `logRequireTitle` / `logRequireDetails` rules.
- **Scope with `includes`.** For example, keep `noRecordInLoop` away from Map/Reduce `map` files:

  ```jsonc
  { "path": "biome-plugin-suitescript/noRecordInLoop", "includes": ["src/**", "!src/**/map-reduce/**"] }
  ```
- **Custom module identifiers.** Generate a rule with your own mapping (and omit `moduleVars`):

  ```sh
  npx biome-plugin-suitescript generate module-vars --set N/record=nRecord --out plugins/module-vars.js
  ```

  then add `"./plugins/module-vars.js"` to `plugins`.

## Tag checker

`@NApiVersion` and `@NScriptType` live in comments, which no Biome plugin can read, so a small CLI checks them.
It is **report-only**: it never edits files.

```sh
npx biome-plugin-suitescript check                      # uses biome-plugin-suitescript.json
npx biome-plugin-suitescript check "src/**/*.ts"        # or explicit globs
npx biome-plugin-suitescript check --format github      # text (default) | json | github
```

It reports (the `@NApiVersion` and `@NScriptType` checks follow the `api-version` and `script-type` rules of both
[acdvs](https://github.com/acdvs/eslint-plugin-suitescript) and [btonasse](https://github.com/btonasse/eslint-plugin-suitescript)'s ESLint plugins):

- `@NApiVersion` other than `2.1` (2.0, 2.x, 1.0 and invalid values), or missing when the file is a script.
- `@NScriptType` with no or an invalid value, or missing when the returned entry points imply one.
- A module from the wrong side of the declared script type (for example `N/file` in a client script), or one the declared type does not support at all (`N/http`, `N/https`, `N/llm` and `N/sftp` in a custom tool; custom modules in a bundle installation script).
- A declared script type that does not match the returned entry points, or lacks its required ones.

Files with no tags and no implied entry points (libraries) are skipped. For scripts still on 1.0, 2.0 or 2.x, the
output points to Oracle's
[`netsuite-suitescript-upgrade`](https://github.com/oracle/netsuite-suitecloud-sdk/tree/master/packages/agent-skills/netsuite-suitescript-upgrade)
agent skill for the conversion.

Exit codes: `0` clean, `1` problems found, `2` usage or configuration error.

### Configuration

List only the **script sources**: files deployed to the file cabinet, or the sources they are transpiled from (not
the transpiled output, and not build files such as `swc.mts`). The CLI refuses to run without a list rather than
guessing from `deploy.xml`.

```jsonc
// biome-plugin-suitescript.json
{
    "$schema": "./node_modules/biome-plugin-suitescript/schema.json",
    "includes": ["src/TypeScripts/**/*.{js,ts}", "!**/*.d.ts", "!**/*.test.*"]
}
```

`!` negation works as in Biome's `includes`. Reuse the same globs in the plugin `includes` in `biome.json` to scope the
Biome rules identically.

## Development

The source is TypeScript under `src/`, compiled by `tsc` to `dist/` (the only code that is published). Scripts and
tests are TypeScript too and run directly on Node. Node and npm versions come from `devEngines` in `package.json`
(also in `.nvmrc` and `.tool-versions`).

```sh
npm install
npm run build          # tsc -> dist/, copies GritQL rules, regenerates biome-manifest.json
npm run typecheck      # tsc --noEmit over src, scripts and tests
npm run check          # biome check (npm run format applies fixes)
npm run sync-modules   # refreshes the N/ module list from @hitc/netsuite-types
npm run readme         # regenerates the rules table above (after npm run build)
npm run docs           # regenerates the per-rule pages in docs/rules/ (after npm run build)
npm test               # builds first, then tests the built package
```

Git hooks (lefthook) run Biome on staged files before commit and reinstall dependencies after checkout or merge.

Commits follow [Conventional Commits](https://www.conventionalcommits.org); release-please opens a release PR and
publishes to npm when it is merged, using npm trusted publishing (OIDC, no token; the package settings on npmjs.com
allow this repo and `release.yml`). Dependencies are managed by Renovate: dev
dependencies are pinned, the `@biomejs/biome` peer range stays a caret, and Biome and `@biomejs/runtime` update together.
