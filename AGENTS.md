## GitHub Actions

Pin every action to its commit SHA with the full semver in a trailing comment, using the latest stable release (look it up with `gh api repos/<owner>/<repo>/releases/latest`), for example `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`. Tool versions come from `package.json` `devEngines` (Node, npm), mirrored in `.nvmrc` and `.tool-versions`; change them in all three. The CI job that tests against the latest Biome is intentionally unpinned.

## Code

Source is TypeScript in `src/` and compiles to `dist/` (gitignored, published). `biome-manifest.json` and `configs/minimal.json`, `recommended.json` and `all.json` are generated by `npm run build` and committed. Run `npm run format` before committing; CI runs `biome ci --error-on-warnings` and `tsc`. Generated files: `biome-manifest.json`, `configs/{minimal,recommended,all}.json`, `src/lib/modules.ts` (`npm run sync-modules`), `src/lib/typings-data.ts` (`npm run sync-typings`), the README rules table (`npm run readme`, data in `scripts/rule-sources.ts`), the per-rule pages in `docs/rules/` and the rule table in `docs/migrating-from-eslint.md` (`npm run docs`; the same data plus the example cases in `test/cases.ts`). Never edit the generated pages or table by hand.

## Rules

Start a new rule with `npm run new-rule -- <ruleName> --tier <1-5> [--grit]`; its `TODO(new-rule)` placeholders fail `npm test` until a human decides each one.

Before adding or changing a rule, follow `docs/rule-priority.md`: source tiers (Oracle agent skills, then type definitions, then Oracle docs, then SuiteScript-specific rules, then generic JavaScript; the lower tier wins a conflict, and a Tier 0 ADR in `docs/adr/` overrides all of them), and default severity and preset placement. Do not add a generic JavaScript rule unless it explicitly benefits SuiteScript and Biome does not already cover it. Assume SuiteScript 2.1 only, and never document backwards compatibility overrides for 1.0, 2.0 or 2.x. Read Oracle docs and skills in full, with every referenced material, never truncated.

## Verification

Oracle's skills, the type definitions and Oracle's documentation contradict each other and sometimes the platform. A claim about what the platform does (what an API accepts or rejects, whether something fails, whether a member exists) needs a verification, or an "unverified" mark. Read `docs/verification/README.md` before adding or changing a rule, or researching how a module behaves. A verified behavior overrides a source's claim about the platform, but never a recommendation unless it proves the recommendation cannot work (`docs/rule-priority.md`, "Verified facts").

- If you can run the test yourself, do. Write a probe in `verification/probes/` and run it in the sandbox with `npm run verify:doctor`, then `npm run verify:run -- <slug> --draft` (`docs/verification/automation.md`, ADR 0007). The doctor's failing steps are the user's to do: relay each and wait. Never run a real deploy or cleanup yourself: the commands refuse `--approved` without a terminal, so ask the user to run the same command in their own terminal, never accept the SuiteCloud license, create credentials or touch production for them. When a probe cannot run (the doctor cannot pass, a script type other than a RESTlet, or a write), prompt the user to run the snippet and paste the output, even when no skill is asking them questions. Do not guess the result, and do not call a claim verified from a paraphrase of documentation.
- When skills, type definitions or documentation contradict each other or themselves, add the contradiction to `docs/verification/contradictions.md`, cite its id in the rule's comment and mark the claim unverified until a test settles it.
- Document every verification as a page in `docs/verification/results/` (the test, the NetSuite version, the results, the explanation and the decision). Never put an account number, account URL, user, token or real record id in it; that is a security risk in a public repository.
- Read "Lessons" in `docs/verification/automation.md` before writing probes: batch them so the user deploys once, and run `probe-zero` after each deploy. When you hit a runner, deploy, probe or sandbox problem that page does not describe, add it there in the same pull request (what happened, what it cost, how to avoid it), and correct any entry that proves wrong.
